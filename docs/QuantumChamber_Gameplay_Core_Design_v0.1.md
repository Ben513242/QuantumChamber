## 1. 核心概念：做成什麼遊戲

### 1.1 一句話玩法

**你在同一位置，走進不同世界；你可以帶走經歷與物品，卻不能保證門外仍是熟悉的地方。**

它不是隨身傳送選單，不是每次清空的副本，也不是實驗室物理模擬器。主要樂趣來自未知探索、固定位置造成的風險、持久世界的辨認，以及多人去留不同而形成的故事。

### 1.2 五項設計支柱

| 支柱 | 玩家感受 | 可落地的實作方向 |
|---|---|---|
| 未知，但不是不明故障 | 我不知道門後是什麼，但知道艙現在在做什麼 | 保持未知目的地；補足準備／等待／鎖定／可跨越／故障訊息 |
| 世界有歷史 | 我以前留下的建築與標記仍然存在 | Universe UUID、catalog、持久 chunks；不重抽已確定身分 |
| 同座標就是代價 | 在 A 是平原，到了 B 可能是懸崖或石頭 | 同 XYZ、方向與既有傳送規則；不搜尋安全點 |
| 一次選擇形成承諾 | 第一個有效選門決定這趟目的地 | 既有 checked selection／receipt；不改成反覆免費重抽 |
| 同行不等於永遠同路 | 有人跨過，有人留下，往後可能重逢 | 凍結參與者與固定目的地；以實際跨越區分去留 |

### 1.3 三種方案與本文件的建議

| 方案 | 內容 | 取捨 |
|---|---|---|
| A：維持單向探險版 | 保留目前 A→走廊→A→B，加提示與探險紀錄 | 最接近現況；無法完整表現連續旅行 |
| **B：錨定式投影端點網路** | 保留現有走廊與分階段傳送，之後允許受驗證投影返航及再次出發 | **本文件推薦**；最貼近原始概念，仍可用 ServerWorld、傳送與 journal 研究 |
| C：字面物理盒子 | 永久唯一內部、任意物質可逆隔離、全歷史分支、同時多宇宙入口 | 延後；會把工程重心轉成另一套空間、存檔與渲染系統 |

推薦 B 的意思不是立即把 A 改掉。交付順序是先讓 A 成為可理解、可驗收的版本，再逐片增加 B 的能力。

### 1.4 世界觀與程式分工

「疊加」是尚未形成確定出口的探索階段；「觀測」是玩家做出有效選擇；「塌縮」是固定此次目的地；「錨定」是維持盒子及端點的身分與控制關係。這些是遊戲語義，不要求計算波函數、能量守恆或實際宇宙拓樸。

基岩、紫色門面、青色控制器、短暫轉場與音效足以建立辨識度。第一版不需要可直接看見另一個世界的傳送門畫面。

## 2. 身分與名詞：避免做錯整套旅行系統

| 名詞 | 正確語義 | 不能混成什麼 |
|---|---|---|
| Universe | 一個有穩定 UUID 的持久世界歷史 | seed；同 seed 可以有不同 Universe |
| Chamber | 一個有穩定 Chamber UUID 的盒子／錨定系統 | 某個世界裡看起來相同的外殼 |
| Root Anchor／根錨 | 該 Chamber 最初註冊的 Origin 與其來源世界 | 每次旅行的出發位置 |
| Projection Endpoint／投影端點 | 同 Chamber 在另一 Universe 的實體位置 | 新的獨立 Origin |
| Entry Endpoint／本趟出發端 | 此 session 真正開始的世界、位置、朝向及端點 | 永遠等於最初的 A |
| Session／本趟會話 | 凍結參與者、候選政策與狀態轉換的一次活動 | 整個 Chamber 的全部歷史 |
| SOURCE | 既有候選中的本趟來源語義 | 「不論在哪裡都回最初宇宙」 |
| EXISTING | 已被系統物化且符合候選條件的宇宙 | 玩家本人一定去過的世界 |
| NEW | 按凍結意圖配置新的宇宙身分 | 複製來源現在的建築、箱子、生物與歷史 |
| HOME／返根錨 | **建議新增**的明確返航意圖 | 偷改 SOURCE 的意思 |

`SourceFamilyRef.Catalog` 目前只是可描述 catalog 來源的型別，**不代表動態 Origin 或 Projection 已可啟動**。[S5]

### 2.1 必須保留的兩個參照

連續旅行設計必須同時保存：

```text
RootAnchorRef = 這座盒子的起源在哪裡
EntryEndpointRef = 這一趟從哪個端點出發
```

例：根錨在 A，玩家由 B 的投影開始新 session。此時中止走廊應返回 B 的出發艙；「返根錨」才是前往 A。不能只保留一個 Source 欄位，讓程式猜兩種不同意思。

這是**新資料設計要求**，不是指示直接往舊 exact-key NBT 塞欄位。具體 schema、codec 與版本必須先設計。

## 4. 玩家完整循環

### 4.1 現在就能維持的核心循環

**建艙／使用服主設置的艙 → 準備裝備與藥水 → 供電、進艙、關門 → 探索走廊 → 選門 → 返回本趟出發艙 → 等待量子膜 → 決定是否跨越 → 探索目的世界 → 保存自己的歷史。**

玩家在走廊選門，不等於立刻從那扇側門走出去。側門負責選擇；真正跨宇宙仍在返回原艙後的量子膜。教學必須把這個差異說清楚。[S3]

現況沒有可靠的常規量子返航。不能在基礎教學寫「回頭進盒子就能回家」。共用 Nether／End 的既定行為可以作為玩家了解的其他路徑，但不是一個已完成的量子返航系統。[S2][S3]

### 4.2 完整建議循環：端點網路完成後

**建設 A 根錨 → 探索並抵達 B → 在 B 建立生活與留下標記 → 回到 B 的投影端點 → 選擇返根錨或再次探索 → 經相同走廊流程抵達 C → 之後可能重訪 B。**

每次新的 session 仍然經歷封艙、藥效與選擇，並非按一本書就從任意位置傳送。

### 4.3 玩家為什麼繼續玩？

早期目標是第一次成功抵達、辨認自己不在 A、在危險出口活下來。中期是找到適合基地的世界、留下識別標記、完成首次重訪與返航。後期是多人分工探險、不同 Universe 的長期建設，以及在同一座標比較不同地形。

不強迫加入新礦物、新怪物或任務劇情。新世界本身、持久建築與共同冒險就能構成主要內容。

## 5. 艙體、取得方式與準備

### 5.1 不為了完整玩法偷偷新增生存配方

**第一個可交付模式：受控探索／伺服器設施模式。**由創造模式、地圖作者或服主建立符合既有規格的艙，玩家以正常生存方式準備裝備與藥水進行旅行。這符合原規格允許創造模式建造、把生存建造儀式列為非核心阻擋項的決定。[S7]

遊戲必須能用創造物品頁、既有指令或目前建造方式完成首次體驗；教學以實際已存在入口為準，不杜撰指令名稱。

**生存取得屬延後的獨立內容包。**可研究以有限材料搭建外殼，再由 Controller 驗證轉成受保護艙，但先不制定配方、成本、返還或破壞掉落。不能為了方便而讓基岩任意合成、量產或掉落。

### 5.2 出發準備

建議教學提醒玩家：帶足食物、工具與方塊，理解海洋、岩漿、懸空、石內等風險；攜帶目前配方可取得的 QuantumState 藥水。不要寫成「帶某件裝備就保證能存活」。

入口附近留出可操作 Controller 的位置，並在第一次啟動前明確顯示「目前版本是否支援投影再啟動／返航」。玩家沒有讀開發文件，也應知道單程限制。

### 5.3 成本與公平性

第一輪建議成本仍是原本的藥水、準備時間、危險與旅行時窗。不新增每個世界的租金、不收取看不見的能量值，也不因伺服器延遲擅自再扣一次材料。

藥效長度、釀造配方、通道倒數的實際值，均從現有註冊與規格取得。此文件不另指定一個未經測試的藥效秒數。

## 6. 走廊、候選與觀測

### 6.1 保留長直走廊與左右側門

繼續使用固定 superposition 維度、有限頁面與邏輯門位。玩家感受是可以往前探索，不必把每一格邏輯距離永久建在物理世界裡。[S3][S8]

同一 session 內，同一門的候選必須遵守既有固定規則。頁面換位、玩家回頭、斷線重連或一般重試，都不能成為重抽該已確定候選的方法。

### 6.2 神祕感的邊界

**保留未知目的地，不增加選前目的地預覽。**選擇前不展示 seed、完整地形、容器內容、是否岩漿或可靠的「安全率」。也不為了顯示提示而先生成所有候選世界。

**建議新增的提示只說操作狀態：**「尚未選定」「本趟已鎖定」「正在返還」「正在準備出口」。目的地資訊依目前規格允許的揭露時點顯示；G1 不改 reveal policy。

第一次有效選擇形成整組承諾。之後再點其他門，應回覆「本趟已選定，無法改選」，不要用無反應代替。

### 6.3 三種目的地的玩家解釋

| 類型 | 對玩家的正確說明 |
|---|---|
| SOURCE | 本趟沒有離開出發世界；不配置新 Universe。未來 B 出發時不能把它誤解為回 A。 |
| EXISTING | 抵達已存在的宇宙；可能是別人發現、你未曾到訪的地方。 |
| NEW | 本次依凍結意圖配置新的宇宙身分；不代表你原本世界被複製。 |

當前 M6 凍結權重為 5／20／75，候選政策版本為 3，capability=0。[S9] 本提案先保留，不提供玩家改權重 UI。這不是保證每 100 次選門恰好出現 5／20／75 次；候選池資格與空池處理仍以原解析器為準。

### 6.4 取消不是重抽作弊

未完成目的地選擇時，依既有牛奶、藥效結束或斷電規則返還。已形成收據之後，取消或失敗不能抹掉該收據並自動改給另一個世界。是否能開新 session 與何時釋放原 session，繼續由既有收尾權威決定。

## 7. 跨門與風險

### 7.1 三個不同時點

**選定目的地 ≠ 出口已準備完成 ≠ 玩家已成功抵達。**

玩家 UI、音效、成就與探險紀錄應分別對應這三個事件。不能在 NEW 配置成功時，就替尚未跨越的人記錄「已抵達」。

### 7.2 通道規則

基線為單向通道；約 60 秒時窗、全員跨越、參與者關門或斷電可使通道結束，實際判定與 timer 沿既有程式。[S3] UI 可顯示遊戲刻推導的剩餘時間，但不能把 TPS 下降時的估計當作準確現實秒數。

已跨越者不因其他玩家留下或之後斷電被拉回。未跨越者留下，不自動投票跟隨、不被強制傳送，也不重開另一個目的地。

### 7.3 安全判定分兩層

**系統安全：**世界身分正確、chunk 準備狀態符合既有規則、資料可讀寫、玩家不是被重複移動。  
**遊戲危險：**世界外面是岩漿、海水、山壁、懸崖或敵對環境。

前者失敗要阻止或安全收尾；後者不應被「善意修正」抹掉。比較器 15 只能表示通道可跨越，不能表示落點安全。

### 7.4 真正應避免的非遊戲性損失

不得因畫面提示誤導、同一請求重複處理、來源與目的世界身分混淆而丟失玩家或複製物品。正常 Minecraft 死亡、地形風險與既定掉落規則，則仍屬遊戲。

## 8. 玩家判讀：不用看 log 也知道該做什麼

### 8.1 不重定義現有比較器數值

| 輸出 | 保留的語義 | 玩家不能據此推論 |
|---:|---|---|
| 0 | INVALID；具體原因可能是結構、停用、非可啟動投影或其他拒絕條件 | 「整個存檔已毀損」；所有 0 不是同一原因 |
| 3 | IDLE，等待符合條件 | 不一定只差紅石，也可能涉及其他條件 |
| 7 | READY，既有資格掃描判為就緒 | 不要求玩家因此再手動製造第二次 rising edge |
| 11 | ARMED 或仍被既有 session／返還收尾占用 | 不保證人現在正在走廊；也不能開始第二個 session |
| 15 | 量子通道準備完成，可依既有資格跨越 | 不保證門後無危險，不保證雙向，不代表所有人已到達 |

這些值沿現有公開行為。[S3] 新的細節顯示使用文字與狀態視圖，不挪用未用數值偷偷改既有紅石設備契約。

### 8.2 建議的三層介面

**第一層：短狀態訊息。**Actionbar／既有訊息管道提供一行狀態，在改變時更新，不每 tick 洗版。  
**第二層：艙體資訊頁。**玩家用新增且明確的互動入口，查看來源、根錨、參與者缺少條件、旅行能力與最後已確認狀態。  
**第三層：管理員診斷。**保留完整 UUID、session ID、原因碼、日誌相關 ID 與資料健康狀態。

G1 先做第一層與簡單文字查詢，未必先做 GUI。不得覆寫既有普通右鍵門控，以及雙手空手蹲右鍵的維護手勢。查詢入口的精確操作方式應在 G1 小規格中訂定；不能為開資訊頁意外切換 enabled。

### 8.3 建議訊息與操作對照

下表的原因名稱是**提案用語**，不是宣稱程式已有同名 enum。

| 玩家狀態 | 建議顯示 | 玩家行動／系統處理 |
|---|---|---|
| 艙體不完整 | 「艙體未完成：請檢查外殼、控制器與整面艙門。」 | 只報已能確定的缺失；不得靠資訊查詢寫方塊修復 |
| 未供電 | 「量子艙未供電。」 | 提示使用原版紅石，不建立新能源系統 |
| 人員未完整入艙 | 「等待參與者完整進入艙內。」 | 不要求 server 為提示掃描全世界玩家 |
| 有人缺少藥效 | 「尚有參與者未取得 QuantumState。」 | 只在符合隱私與距離範圍時列隊員名稱 |
| 走廊啟動 | 「疊加通道已建立。任一隊員藥效結束，整組返回。」 | 只在此次 session 真正成立後顯示 |
| 選擇成功 | 「目的地已鎖定。正在返回出發艙。」 | 不讓玩家誤以為側門即時開啟 |
| 重複選門 | 「本趟已鎖定，不能改選。」 | 不重新配置世界或收據 |
| 正常準備中 | 「正在準備出口，尚不可跨越。」 | 不顯示沒有實測根據的完成秒數 |
| 目標有玩家阻擋 | 「目的艙位置有人，正在等待。」 | 不把玩家推走／刪除，不改換目的地 |
| 設定重載暫停 | 「設定更新中，量子艙暫時不可使用。」 | 僅在 server 確認這個原因時顯示 |
| 收尾仍有離線者 | 「正在等待本趟參與者完成返還。」 | 不把離線當死亡、不強制清 journal |
| 通道可跨越 | 「通道已就緒：同座標、單向，出口可能危險。」 | 允許符合資格者依原流程跨越 |
| 已成功抵達 | 「已抵達宇宙 U-…」 | 經移動及身分驗證後才顯示、寫入到訪紀錄 |
| 目前版本不支援投影啟動 | 「這是目的地投影。本版本無法由此啟動旅行。」 | 使用實際能力而非未來宣傳文案 |
| 未來根錨不可確認 | 「目前無法確認根錨狀態，暫不能出發。」 | UNKNOWN 不等於 OFF 或 DESTROYED |
| 資料健康異常 | 「旅行已暫停，請保留存檔並聯絡管理員。參考碼：…」 | 不叫玩家刪除 dat、不假裝重試會自癒 |
| SOURCE 結果 | 「本趟出口仍通往出發世界。」 | 不顯示「新宇宙已建立」 |

`SEALED`／準備阻擋／普通門關閉應在文字上區分。資料流程封鎖不等於玩家永遠不能以現有普通門控離開；不要因新 UI 重新鎖死人。

### 8.4 狀態訊息不得創造新行為

所有顯示由 server 權威狀態投影。UI 查詢不得：建立新 Universe、提前 resolve 候選、消耗藥水、發放收據、呼叫傳送、清理 journal、恢復投影或觸發新 session。

建議以狀態轉換事件更新，輔以低頻讀取已在記憶體的狀態。具體頻率透過 profiling 決定；不為每個玩家每 tick 讀取整份 catalog 或磁碟。

### 8.5 顯示真相，不猜理由

只有比較器 0 時，沒有足夠資料就顯示「無法啟動，詳見狀態」，不能推測成「未供電」。失敗時也不能把 Unknown 顯示為「錨點被毀」。如果原因讀取失敗，保留已知最後狀態並標示過期。

顏色、聲音只是輔助。重要狀態必須有文字，不依賴 shader、色覺或特定資源包。

## 9. 宇宙辨認與探險紀錄

### 9.1 世界身分不是外觀

**保留：**同一 UUID 指向同一持久世界歷史；same-seed fresh 只重用生成 seed／設定，不複製玩家建築與已經發生的歷史。[S6][S10]

玩家看見相似山形，不能因此判定「回家了」。玩家看到自己先前留下的標記，加上 server 回報相同 Universe UUID，才是可操作的辨識方式。

### 9.2 建議新增「探險紀錄」

先用簡單列表或文字頁完成，不強制新 3D UI。

| 欄位 | 說明 |
|---|---|
| Universe 短代號 | server 產生的顯示代號；完整 UUID 仍是身分權威 |
| 玩家命名 | 例如「海上出口」「山洞基地」；只是標籤，不是世界 key |
| 初次／最近抵達 | 以成功傳送驗證事件為準 |
| 經過哪座艙 | Chamber UUID 與出發端點的可讀標籤 |
| 玩家備註 | 自己記下危險、建築或會合資訊 |
| 紀錄時間 | 遊戲時間或 server 記錄時間，清楚標單位 |
| 已知能力 | 本版本是否可從該端點返航／再次啟動 |

短代號須處理碰撞；不能只截 UUID 八碼就把它當唯一鍵。命名必須有長度、控制字元與權限限制，禁止把玩家輸入直接當檔案路徑。

### 9.3 不能把紀錄冊變成世界控制權

紀錄頁可以被複製或分享，但它不應授權傳送、指定任意 world key、取得對方基地權限或重建已毀錨點。路由資格仍要由 server 檢查已確認的世界與端點資料。

「系統已有這個宇宙」與「玩家已到訪」分開保存。玩家備註不是目前即時地形；寫「安全」也只能表示過去的觀察。

### 9.4 到訪紀錄和傳送權威分層

建議把日記視為已確認旅行事件的衍生資料，可用既有收據或新的事件 ID 去重。若日記寫入失敗，不應在玩家已成功抵達後把同一次傳送再執行一次。

但 endpoint／路由權威資料的寫入失敗，不能用「日記可稍後補」來掩蓋。兩者要分清楚。

### 9.5 成就與獎勵

建議先做不改經濟的進度：第一次抵達、首次存活返根錨、重訪同一世界、兩位分離隊友重新會合。以成功事件去重，不因重連或重播收據反覆觸發。

先不發放可大量複製的稀有材料，也不給每次 NEW 固定高額獎勵，避免鼓勵無限制建立世界。目標是讓世界值得留下，而不是刷出後丟棄。

## 10. 端點網路：完整旅行的建議主線

**狀態：需設計閘門；不是 M6 現有功能。**

### 10.1 採「投影代理」，不是隨便把投影改成 Origin

A 保持該 Chamber 的根錨。B 的投影若被新能力批准啟動，應代理同一 Chamber；不得重新配一個 Origin 身分，或把 local redstone 當成根錨所有權。

最小前置條件包括：confirmed projection 記錄、exact Universe／world、正確位置與朝向、對應根錨仍有效、相容的權威資料、沒有同 Chamber 的衝突 session，以及足夠的有界資源。

不符合時維持 inert 與明確提示。**不可只刪掉 `ChamberPowerCoordinator` 的 PROJECTION／role 防線。**[S11]

### 10.2 先做 B→A 返航，再做 B→C 新探索

第一個旅行擴充只允許有效投影要求「返根錨」。目的地固定，無須 NEW 配置、無須選機率，也不需要完整雙向同時開門。

返航仍是一趟新的、受驗證的**單向**通道，不是原先 A→B 通道永遠反向保持開啟。玩家必須回到投影艙，不得在野外使用物品瞬移。

本提案建議返航採固定目的地模式：「資訊／路徑頁選返根錨 → 全員資格與封艙 → 固定目標準備 → 出發端量子膜 → A」，不必走未知候選走廊。它仍需完整 session、參與者及收據，不是 UI 直接 teleport；只能重用已確認相容的準備／通道／復原元件。探索模式繼續走原本的走廊。入口不能搶占現有維護手勢，精確互動與新狀態轉換在該切片的 binding spec 訂定。

### 10.3 根錨在原版 A，不能假裝它是 catalog U

現有目標解析與 world descriptor 很多路徑只面向動態 Overworld。返根錨需要分清 vanilla root 與 catalog world；不可捏造一筆 UniverseRecord 讓 canonical A 假裝是新 U。

**返根錨只能驗證既有 A 原艙，不得對它呼叫投影 FIRST_WRITE。**根錨內既有方塊與容器不能因返航被清空；原艙不合法時應拒絕或進入維護狀態，不能自動重建為投影。

也不能把某次舊的 `UniverseTransferReceipt` 當永久跨重啟返航票。內存中的 world instance token 只能驗證當次 live instance，重啟後要由持久身分重新解析並驗證目前實例。

### 10.4 再做投影出發的完整探索

B 的投影啟動後，流程維持：

```text
B 投影艙 → 本趟走廊 → 選門 → 返回 B 出發艙 → B 的量子膜 → C
```

不改為「走廊側門直接傳到 C」，以減少同時改動幾何、回復與旅行流程的範圍。

同 seed／toggle 類型必須以 **本趟 Entry 所在 B 的已確認生成權威** 為來源，而不是拿根錨 A 的 seed／preset 代替；EXISTING 的來源排除也依本趟來源。根錨提供身分與運作條件，不應偷偷改變新宇宙的生成參考。舊 frozen policy／intent 仍保留舊語義。

此時：

```text
Root = A
Entry = B
SOURCE = B
HOME = A（新意圖，與 SOURCE 分開）
EXISTING / NEW = 既有候選系統凍結的目的地
```

### 10.5 本提案不要求永久單一內部

每一趟仍可租用新的走廊 slot。玩法上是同一套量子艙系統，程式上是不同 session 的暫時空間。玩家不必在走廊內建永久倉庫，其他端點也不必同時看見同一個內部。

這是刻意選擇的遊戲化轉譯，不是假裝現況已實作真正共同時空。

### 10.6 同一 Chamber 一次只開一個 session

第一版端點網路對同 Chamber 全域序列化。A、B、C 同時按啟動時，由 server 原子地接受一筆，其餘顯示「此錨定系統已有旅程進行中」。已接受者的參與者與 Entry 不得被後來的請求覆寫。

不同 Chamber 是否可並行，沿現有資源與全域碰撞規則，不為了序列化一座艙而鎖住整台伺服器。

### 10.7 自選已知航路延後

返根錨和隨機探索完成後，才研究「同一 Chamber 的已確認端點」書籤。第一版不提供任意 UUID 傳送、不跨 Chamber 跳到別人基地、不因持有一本書就增加權限。

需要另設顯式路由意圖與稽核，不得偽裝成隨機 EXISTING，從而破壞既有凍結候選收據。本文不把自選航路列為基礎版必要功能。

## 11. 多人、死亡、離線與分離

### 11.1 凍結參與者

保留既有入場資格與 cohort。不能在中途把路過者自動加進本趟。非參與者不能跟著量子膜偷渡；騎乘、掉落物、一般生物等限制沿目前階段政策，不因玩家期望而默默放行。[S3]

第一版不增加隊長投票、全員確認 GUI 或個別玩家選不同門。第一個有效選擇鎖定整組，其他選門被拒絕；這是明確的多人規則。

### 11.2 分離發生在真正跨越時

例：甲乙選好 B，甲跨過，乙留在 A。通道結束後甲在 B、乙在 A。系統不複製甲，不把乙強制送過去，也不替乙重新開另一扇門。

未來端點網路仍不能讓甲在舊 session 尚未收尾時，從 B 搶開同 Chamber 新 session。先完成關閉與釋放，再開始下一趟。

### 11.3 藥效與牛奶

在既有走廊階段，任一凍結參與者藥效失效，整組依既有規則返回本趟出發艙；已花費的藥效不退款。[S3] 不新增「只有喝牛奶的人回去、其他人留在原 session」的分叉。

已經完成跨宇宙旅行後，不因舊藥效到期追溯撤回旅行；移動結果由已確認事件決定。

### 11.4 死亡與床點

保留 M6：有效床／重生錨依原版優先；只有在 exact live U 主世界死亡且原版要 fallback 到 canonical 時，改留同 U，位置依原版規則。[S2][S4]

不能簡化成「在 U 死亡永遠回 U」，因為有效床點可能在別處。海上 spawn 落海底屬已列出的行為，不能在這份提案中偷偷加安全 Y 修正。

死亡不重新生成宇宙，不把 Universe UUID 換掉。物品與其他死亡規則沿原版及伺服器設定。

### 11.5 Nether／End

明確教玩家：各 U 共用原版 Nether／End；地獄門回程預期回原版主世界；End 出口依原版床點等規則。這與死亡 fallback 是不同機制。[S2][S4]

本提案不加防堵這些路徑的 portal hook，也不為了強化「被困異世界」敘事而改變已接受範圍。

### 11.6 離線與重啟

先保留目前 pending recovery 行為，不為改善等待感而強制清除未完成參與者。玩家 UI 應說明正在等待收尾，管理員有對應 session 診斷。

未來要解除離線者對整組的阻擋，需另設每玩家 escrow／返還責任與重連狀態；這不是 G1 的文字優化，也不能用 timeout 後刪 journal 代替。

## 12. 投影佔位：保留遊戲威力，也誠實揭露代價

### 12.1 預設維持現有「投影覆寫」

第一次寫入改造整個 7×7×7，內部清為空氣；既有容器會先被清空，不掉出物品。與寫入區相交的非旁觀玩家會阻擋，但其他實體目前不做安全搬離。[S6]

這是破壞性玩法，不應在教學裡說成「物質暫時存到另一空間」。危險警告須在第一次啟用教學與服主說明中出現；不用每次開門彈出阻擋流程的法律條款式對話。

### 12.2 保留外部世界

艙體保護範圍不延伸成自動安全區。投影外面的水、岩漿、山壁、建築、洞穴及敵對環境照常存在；不自動移走。

此規則也影響其他玩家的建築。多人伺服器是否允許任意人建立新的根錨，應有服主政策；第一版可維持服主／地圖預設艙體模式，不自動做跨模組領地系統整合。

### 12.3 衝突不是靠最後寫入者贏

其他 Chamber、既有 Controller、玩家阻擋與世界範圍等衝突，沿權威記錄與現在的 fail-closed 規則。不能為了符合「絕對」一詞，刪除別人的錨點或改掉資料身分。

### 12.4 撤除與死盒

現在沒有原物質恢復能力。Origin 拆除後，既有投影記錄與保護可以保留，形成 Dead Chamber。[S12] 不宣稱把一切回復成投影前的世界。

重新放置外觀相同的 Controller，不得因此冒充已摧毀根錨的原 UUID。修復硬體與復活已毀身分是不同操作。

### 12.5 可逆佔位只做未來研究模式

若未來研究，可先限於新建測試世界、有限區域與明確支援的 block state／block entity；完整盤點 fluid、scheduled tick、POI、跨邊界關聯、entity、外掛資料與玩家改動。

先寫可驗證的 before-image，再寫投影；恢復前確認佔位者與區域版本。出現新物件或改動時拒絕自動覆寫，不能把玩家後來放進來的物品洗掉或複製。

沒有這套支援清單與原子提交／重啟恢復規則之前，不加入「撤除即完美恢復」按鈕。已被舊版本覆寫而未保存的資料，不能靠新功能恢復。

## 13. 紅石、根錨失效與資源邊界

### 13.1 紅石是運作許可，不是電力模擬

保留原版供電規則。世界觀可描述成「錨點維持聯繫」，程式不需要新增瓦特、跨宇宙線損、燃料發電與熱力學系統。

遊戲中的「一直有電」只代表權威條件成立，不代表已實作真實跨宇宙能量守恆。

### 13.2 未來端點網路的根錨檢查

投影出發前需要讀取 A 根錨，而不是只相信 B 存著一個過期 `powered=true`。但也不能永久強制載入所有投影或全部世界。

建議用有界的根錨及供電鄰域載入／驗證租約：有限數量、有限準備工作、明確釋放責任，並區分 `ON / OFF / UNKNOWN / DESTROYED`。根錨未載入時先是 UNKNOWN，不能直接認定斷電或被毀。

這部分要先核對現有 ticket 與 session pin 所有權，不能疊加一套永不釋放的 chunk loader。

### 13.3 中途斷電的階段表

| 發生時機 | 建議結果 |
|---|---|
| 還沒開始 session | 拒絕出發，保持世界與玩家狀態 |
| 走廊尚未選門 | 按既有收尾流程回 Entry；未來 B 出發就回 B |
| 已有選擇／正在準備 | 保留已確認目的地與收據；按該階段契約等待或收尾，不重抽 |
| 通道已開、有人未跨 | 關閉旅行能力並完成既有收尾；未跨者留下 |
| 玩家已完整到達 | 不拉回，不刪其背包，不消滅目的世界 |
| 正在移動、結果不確定 | 依實際身分／位置和 journal 收斂，不以「重試 teleport」當萬用修復 |

這是未來端點版的目標規則；現有階段是否能直接沿用須在 binding spec 映射，不得只在 UI 階段實作。若 Entry 已遭破壞、來源世界不可解析或權威損壞，就不能承諾仍然安全返回；應保持既有保守回復／託管語義與證據，明示 pending 或維護需求，不任意改送別的宇宙或刪除記錄。

### 13.4 根錨摧毀

已抵達的玩家仍在目的世界，既有世界與投影不刪除。新出發及返根錨被拒絕；留下可辨認的失聯／死盒狀態。不以瞬間全服刪盒作為效果。

同 Chamber 的根錨轉移、復活或接手不是本輪功能。管理員救援只能使用明示的維護流程，記錄來源、目標與執行者；不把管理員傳送偽裝成宇宙自然重接。

### 13.5 容量與伺服器公平

「世界永久保存」不等於能無限制同時運作。既有 64 corridor leases、4096 chunk coverage，以及每 session 候選容量是不同維度的限制，不能混稱成「宇宙最多 64 個」。[S8][S9]

G1 先顯示已存在的容量拒絕，不改資源政策。若後續加入 NEW 世界總量／生成配額，必須在意圖不可逆提交前設計 quota reservation；不能配置到一半才換成其他候選。

暫時不能建立 NEW 時，不刪舊世界，不回收其 UUID，不把稀有度重抽到能過為止。是否仍可重訪既有世界，由實際載入能力決定，不應一刀切地把舊世界永久封死。

世界池卸載與大規模容量優化保持獨立設計，不是此文件授權順便實作的功能。

## 14. 畫面、聲音與敘事呈現

### 14.1 低成本而清楚的識別

保留基岩外框、紫色艙門、青色 Controller 的既有語彙。建議用短提示音區分「符合資格」「選擇鎖定」「出口就緒」「拒絕」。不依賴 bloom、動態光照或特殊材質讓玩家判斷是否安全。[S7]

失敗音與危險環境音分開：前者表示系統未完成旅行，後者是世界正常風險。

### 14.2 不假裝看得見另一個世界

量子膜可維持不透明／抽象效果。若第一版沒有目的地渲染，文案就不寫「看看門後再決定」。跨越後的短標題、環境切換與相同座標，已能產生足夠的反差。

不在每次換頁播放長動畫，不用不可跳過過場掩蓋等待。準備耗時不可預知時說「準備中」，不播放假的 99% 進度條。

### 14.3 教學順序

第一次接觸艙體：解釋同座標與單向風險。第一次進走廊：說明選門會把整組帶回出發艙。第一次通道就緒：指出真正跨越入口。第一次抵達：解釋 Universe 身分與目前返航能力。

教程記錄不是安全權威；重置教程不能重抽候選或改世界。每次旅行仍顯示必要短提示，不強迫重看完整說明。

## 15. 技術落地方式與改動邊界

### 15.1 對現有模組責任的建議對應

| 功能 | 可先檢查的現有位置 | 改動邊界 |
|---|---|---|
| 啟動與拒絕原因 | `chamber/ChamberPowerCoordinator.java` 與啟動資格服務 | G1 只增加可讀觀察，不改 Origin／Projection 權限 |
| 候選身分 | `candidate/CandidateResolver.java`、`M6CandidatePolicySelector.java` | 不改舊 policy、HMAC domain、權重與 frozen context |
| 來源語義 | `candidate/SourceFamilyRef.java` | 型別存在不代表已開放動態來源 |
| 塌縮階段 | `collapse/CollapsePhase.java`、`CollapseService.java` | 把現有狀態映射成顯示；不另寫第二套旅行狀態機 |
| 實際跨越 | `collapse/PassageService.java`、`universe/UniverseTransferService.java` | 保持 exact identity、前後核對及失敗回復；未來 Root 目標需專門設計 |
| 危險落點政策 | `collapse/PassageTransferPolicy.java` | 不加 safe landing 或更改 XYZ |
| 投影材料化 | `collapse/ProjectionWriter.java`、`ProjectionLedger.java` | 保留 FIRST_WRITE／REPAIR 差異，揭露破壞性；不在 G1 加 restoration |
| 投影保護與失聯 | `collapse/ProjectionProtectionIndex.java` | 不用資訊頁重新寫入權威或解除死盒保護 |
| 走廊容量 | `corridor/SlotAllocator.java`、`CorridorPageManager.java` | 不移除上限來假裝無限，不重建永久公共房間 |
| 到訪紀錄 | 已確認傳送結果的衍生事件／新獨立日記服務 | 不改 catalog 的 Universe 身分權威 |
| 存檔 | `persistence/*`、既有 checked 寫入與復原流程 | schema 變更先設計，不手改舊 dat 解鎖 |

這是檢查入口，不代表完成了逐行呼叫鏈審查；實作者仍須確認該 checkout 的實際程式。

### 15.2 G1 的狀態視圖

建議建立只讀的 `ChamberStatusView` 類概念，欄位可含：現況代號、拒絕原因、參與者數量、允許的操作、資料新鮮度、session 對應、目前旅行能力。

名稱是示意，不指定一定新增同名類。先由現有服務產生穩定只讀快照，再由 UI 消費；不要讓 client 自行推導 server 的關鍵狀態。

Yarn 1.21+build.9 的 `ServerPlayerEntity` 已有 HUD 訊息與跨世界 teleport 等基礎介面；這只支持採用既有遊戲機制的方向，不證明新的端點恢復流程已經正確。[S17]

單人 integrated server 與 dedicated server 都走同一權威邊界。需要同步封包時，用本版本已支援的 Fabric 機制，包含 session／revision 對應與大小限制；過期訊息不能覆蓋較新的旅行結果。

### 15.3 端點啟動前的設計閘門

必須先回答並以小型測試證明：

1. B 的 Projection 如何驗證同 Chamber 的 A 根錨，而不把 B 註冊為新 Origin？
2. 返還服務如何辨別 Root 與 Entry，並在任何中止路徑回到正確 Entry？
3. Vanilla A 返航與 catalog U 的 target authority 如何分派，而不偽造 UniverseRecord？
4. 同 Chamber 多端點競爭，在哪個原子提交點取得 session 使用權？
5. Crash／disconnect／reload 發生於接受請求、寫入意圖、移動、確認各邊界時，如何續行而不重複物化？
6. 根錨 chunk／供電鄰域的 ticket 有誰取得、誰釋放、上限是多少？
7. 舊 world／舊 session 如何維持原語義，新功能需要哪個明確的 capability 與 schema 版本？

若其中任何題仍靠「大概沿用」回答，就還不能開始放寬 production guard。旅行能力版本與 `FamilyCapabilityVersion` 不得混用；新增投影旅行不能把目前明確為 0 的 family capability 改成 1，讓它錯誤宣稱已具備專屬 Nether／End。

### 15.4 重啟與動作冪等性

新的玩家操作應綁定 server 產生的穩定請求／session 身分。重複封包、重連、GUI 重點，只能重讀已確認結果或續行既定流程，不能重複扣料、重複建立世界或重複傳送。

不要宣稱跨 Minecraft 全部存檔具有全域原子交易。應沿既有多份權威資料、檢查點與復原邏輯，明確列出每個可能半完成的狀態。

### 15.5 禁止的捷徑

不能靠刪 `quantumchamber_sessions`／allocation／projection 檔清障，不能重用 Universe UUID，不能把網路失敗視為玩家未移動，不能把失敗世界換成新 seed 假裝同一個目的地，也不能在新 UI 按鈕裡直接呼叫無權威檢查的 teleport。

## 16. 開發階段：小步完成完整玩法

### G0｜完成原定 M6 收尾

**不是新功能。**沿最新人工清單與裁示完成單人、多人、宇宙重生、release JAR 與 `/reload` 驗證，填實際證據。原 FAIL、waiver、同 SHA 範圍與合併／tag 權限保持原規則。[S2][S4]

不要求因本提案重跑已結案的 T13，也不在此時插入投影啟動、世界快照或全新存檔格式。

**出口條件：**既有 M6 的應完成事項都有真實狀態，沒有把自動通過當成人工已做。

### G1｜玩家判讀與教學（優先建議的下一個小切片）

**內容：**狀態原因、三時點訊息、單程／投影能力提示、第一輪教學。現有程序不變；先不做日記持久化或大型 GUI。

**複雜度判斷：**低至中；主要風險是讀狀態時觸發副作用或誤導玩家，不是物化新世界。

**出口條件：**讀資訊不改世界；一般玩家不看 log 也能分辨缺藥效、準備中、已鎖定、出口就緒及系統暫停。

### G2｜探險紀錄與身分辨認

**內容：**抵達後記錄、可讀短代號、玩家標籤、同一宇宙重訪辨認。先只記錄，不加任意航路選擇。

**複雜度判斷：**中；需要清楚的衍生資料寫入、去重與損壞處理，但不改旅行決策。

**出口條件：**紀錄失敗不重做傳送；未跨越者不被記為到訪；名稱與短碼不能被當成真正 UUID。

### G3｜投影返根錨（先設計，後實作）

**內容：**只有已確認投影可啟動新的 B→A 返航意圖。保持同座標與單向通道，不做 B→NEW，不做永久雙向門。

**複雜度判斷：**高；涉及來源端、根錨權威、通道 target、session 恢復及 schema，不是 UI 任務。

**出口條件：**A→B→A 在單人、多人、重啟、部分跨越、斷電與 root unknown／destroyed 下都有明確且可測的結果。

### G4｜投影再次探索，完成 A→B→C

**內容：**允許被新 capability 批准的 B 投影開新 session；回復先回 B，再由 B 通道前往 C。Root 保持 A。

**複雜度判斷：**高；重點是 Entry／Root 不混淆，不是增加地形生成器。

**出口條件：**SOURCE 在 B 出發時確實表示 B；中止回 B；HOME 才回 A；舊 session 不被重解讀。

### G5｜遊戲內容打磨

**內容：**依實玩結果增加成就、日記可用性、短音效與多人教學；生存建艙可另外起案。是否加入同 Chamber 已知端點書籤，獨立決策。

**出口條件：**新增內容沒有改壞核心權威、沒有誘導無限刷世界、沒有把未知探索變成免費傳送清單。

### 不排入上述主線的研究

可逆物質保存、全歷史微差分支、永久共同內部、所有生物與載具搬運、即時異世界視窗、時間流速差異、完整 Nether／End family、全域 eager 投影、世界池卸載。它們不是本提案宣稱的「下一步順便完成」。

## 18. 三個完整體驗案例

### 案例一：陌生而相似的世界（基礎版可表現）

玩家由 A 出發，選到 same-seed fresh 的 B。山形相似，但 A 的房屋不在。抵達提示給出不同宇宙代號；玩家在 B 放置告示與基地，再次透過已存在候選抵達相同 B 時，自己的建築仍在。

**判讀重點：**相似地形不等於回 A；同 UUID 重訪才是同一世界。即使外觀看似沒變，也沒有模擬「只差一個原子」。

### 案例二：隊伍分離（基礎版可表現）

甲乙共同選到 B，返回 A 後，甲先跨越，乙決定留下。通道關閉。甲不會因乙沒走而被拉回；乙也不會被強制跟隨。日記只為甲記錄到訪 B。

未來有端點返航能力時，甲可以走回 B 投影，另開新 session 返 A；在那個功能上線前，教學必須明說沒有這條常規量子回程。

### 案例三：A→B→C 與正確取消（G4）

根錨在 A。玩家由 B 的同 Chamber 投影再出發，但走廊內藥效到期，回到 B，而不是 A。補齊條件後再出發，這次選到 C 並跨越。最後由 C 的返根錨意圖回 A。

**判讀重點：**Root 一直是 A，Entry 隨每趟改變；取消、SOURCE 與 HOME 分別有不同意義。
