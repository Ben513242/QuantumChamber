# M1.2：單人供電與原艙保護設計

日期：2026-09-17。程式基準：`873b3356cedb8bfb76f330341d706cf8c8f1ff1b`，分支 `feature/m1-chamber`。

**狀態：2026-09-17 使用者已核准本規格（含可選照明與安全策略）並授權實作。尚未完成，不能當作遊戲操作現況。**

> 後續狀態（2026-09-24）：上行為核准當時的歷史快照。M1.2 其後已在 `feature/m1-chamber` 實作並完成自動 gate，人工驗收（主副手火把、日夜粒子、shader 等）仍待記錄；見 [M1.2 紀錄](../../implementation-notes/m1.2-powered-origin.md)。合併狀態以 `main`／tag 為準。

## 1. 核准玩法與歷史契約

- 有效艙體在外部紅石供電後就註冊、取得 UUID 並保護；不要求玩家、QuantumState 或門關閉。
- 供電時普通右鍵 Controller 仍能開／關整面門，單人可以從外部供電後再進去。
- 玩家進入、關門、所有艙內參與者有 QuantumState 後，自動進入量子啟動流程。可先喝藥或進艙後喝，不要求第二個紅石上升訊號。
- 持續供電不能重複建立同一艙體的活動 session。
- 外部斷電時，先安全返還走廊玩家、結束延伸空間，再解除原艙保護。返還實作屬於配套的 [M2 設計](2026-09-17-m2-powered-corridor-design.md)。
- 只有建立艙體的原始宇宙具備停用／拆除權限；其他宇宙的投影不得因此解鎖。
- 關門後太暗，需提供手持火把照亮普通艙內及走廊的客戶端方案。

這些新核准規則取代 M1.1 契約中「所有前置條件必須先成立，成功紅石上升訊號才註冊／保護」與「斷電不解鎖」的玩法目標。M1.1 文件仍保留為舊版實作及驗證紀錄；舊測試結果不能當作新版驗證。

## 2. 範圍與環境

- Minecraft 1.21、Yarn 1.21+build.9、Fabric Loader 0.17.2、Fabric API 0.102.0+1.21、Fabric Loom 1.7.4、Java 21、Gradle Wrapper 8.8。
- 單一 Fabric module，維持 main／client 分離及 `splitEnvironmentSourceSets()`。
- 外殼 7×7×7、內部 5×5×5、Controller local(3,6,0)、25 格 Bulkhead。
- 保留 Bedrock、Quantum Bulkhead、Chamber Controller 三種建材、既有方塊 ID 與青紫造型。
- 不改原生基岩強度；目前拆改驗證使用創造模式。
- M1.2 不建立 Dimension、Universe、走廊或傳送；M2 才提供實際延伸空間。
- 不新增 `LICENSE`，不合併／推送 `main`，不刪除玩家世界。

## 3. 建議的服務邊界

兩種可行方式是擴充既有 `ChamberRedstoneService` 包辦全部生命週期，或保留它作為輸入介面、抽出供電協調服務。採用後者，讓供電、資格與返還有各自可測試的邊界。

- `ChamberRedstoneService`：讀取原生 received power，處理鄰居、開關門、載入與有限週期刷新。
- 供電協調服務：驗證原艙身分、提交註冊、更新供電保護狀態、請求啟動或斷電返還。
- `ChamberActivationService`：唯讀評估有效 shell、sealed、非 spectator 參與者、全員 buff、管理 enabled 與無活動 session；不把新 rising edge 當量子啟動必要條件。
- `ChamberProtectionService`：讀取已發布的保護狀態及完整原艙身分，不在每次方塊修改時載入 PersistentState、掃描結構或強載 chunk。
- session 介面：M1.2 僅能明確表示「沒有 session」；M2 接入真實啟動與返還。不得在 session 狀態不明時回傳虛假的「已返還」。
- `ChamberLifecycleService`：管理 enabled、身分與實際移除後的 Registry／索引清理，不把紅石斷電當作 destroy。

## 4. 供電、啟動與關閉

供電狀態與管理 `Enabled` 分開，不能把 schema1 的 `Enabled` 重新解釋成 powered。一般操作保持管理 enabled；既有原艙停用手勢可停止量子功能，但不能在仍供電時繞過防拆保護。M2 的管理停用也必須先完成安全返還。

```text
有效草稿＋未供電：不註冊、無保護
        ↓ 外部供電
POWERED：註冊／保護，可開門；等待玩家、關門與藥水
        ↓ 條件成立，且沒有活動 session
啟動請求：M1.2 停在 ARMED；M2 建立真實 session
        ↓ 外部斷電
RETURNING：停止新啟動，原艙仍受保護
        ↓ 明確確認返還與 session 結束
OFF：僅原艙解除保護，UUID／Registry 記錄暫保留
```

- 結構有效與 sealed 分開判定；門開著不妨礙供電註冊，但禁止進入量子態。
- 至少一位完整位於 interior 的非 spectator 玩家；所有被納入的玩家都必須有 QuantumState。
- 同一艙體的啟動、返還、拆除在伺服器執行緒序列化；返還未完成時，即使又供電也不能搶先開新 session。
- 新增藥水、關門與有限週期刷新都可觸發資格重評，不需玩家離艙撥第二次拉桿。
- M1.2 尚無走廊，ARMED 不消耗 buff；M2 成功入場才依原設計原子消耗全員效果。
- 載入時讀取實際電位並協調狀態，不製造假 rising edge，也不將 NBT 的高電位快取當作永久事實。
- 放置或載入時已供電，可依當下有效結構註冊與保護；這是新版電位條件，不是合成一個紅石邊緣。重啟有舊 session 時先恢復，不直接另開 session。
- Registry 不健康、身分不一致、無效結構或重疊拒絕時，不留下新的半完成註冊。

## 5. 保護、身分與拆除

- POWERED、RETURNING、未完成載入協調的已註冊艙體保留保護。
- OFF 且返還完成時，只有核對為原艙的位置可在創造模式正常拆改；不能只憑同 role、同 XYZ 或玩家當前維度解鎖。
- 保留 UUID、Origin world key／role、anchor、facing、instance kind、Registry 健康與非 destroyed 的身分檢查。
- M3 尚無 Universe backend；M1.2／M2 以既有原始 vanilla world 身分拒絕非原艙操作，不能宣稱已完成真正跨宇宙 live 驗證。
- 停電不刪除 UUID、不刪世界；未拆 Controller、重新修好並供電時沿用原 UUID。
- Controller 確實移除後才清除原 record、所有相交 chunk 索引及失效 queue；原生移除失敗時不得提前清理。
- OFF 拆其他牆面後，記錄可以保留待修復；拆 Controller 後才釋放碰撞占位，避免 ghost record。
- 權限仍屬原艙／原宇宙，不新增玩家個人 owner 或 OP 限制。

## 6. 比較器與維護提示

| 情境 | 輸出 |
| --- | --- |
| 無效／管理停用／未供電且已完成返還 | 0 |
| 有效且供電，但關門／玩家／藥水條件未齊 | 3 |
| 資格成立、等待啟動提交 | 7 |
| ARMED、M2 活動 session 或正在返還 | 11 |

不使用 15，不假裝已有跨宇宙 passage。未供電與結構無效的文字提示必須區分；比較器同為 0 不代表結構一定損壞。普通右鍵門控在未供電／管理停用時仍可使用。

## 7. 手持火把：可選客戶端方案

建議使用 LambDynamicLights，不自行新增 renderer、Sodium mixin 或伺服器隱形光源方塊。

- 官方 [3.1.4+1.21.1 發行頁](https://modrinth.com/mod/lambdynamiclights/version/3.1.4%2B1.21.1) 列出 Minecraft 1.21–1.21.1、Fabric／Quilt、client-side 與 Fabric API 相依性，作為固定環境的候選版本。
- 官方 [專案說明](https://github.com/LambdAurora/LambDynamicLights) 說明手持發光物品會提供動態照明。
- 這是已核准的選用客戶端模組，不列為 QuantumChamber 的 mandatory dependency，不內嵌／複製第三方程式，也不提交第三方 JAR。
- 保留乾淨的 `client-base` 與 dedicated server；新增明確的照明啟動選項及指引，不默默汙染 baseline。
- 主手／副手火把、收起火把、關門艙內、M2 走廊與返還後都列入人工照明檢查。
- 開啟選項但模組缺少或載入失敗時明確提示，不假裝已照亮；未安裝時量子玩法仍可執行。
- 動態光源只影響客戶端視覺，不替代 QuantumState、不變更原生世界光照與刷怪規則。
- Sodium／Iris／shader 相容性以精確版本人工驗證，不從支援 1.21 或編譯成功外推。

## 8. 舊世界與驗證交付

- 讀取 schema1 時保留既有 UUID、Enabled、Destroyed、world／role、anchor／facing，不推測過去是否真正紅石啟動。
- 新的供電／返還狀態以明確版本化 NBT 保存；舊 record 先採保守保護，再於原 world 的安全載入流程重讀電位。
- 損壞或未知 schema 不覆寫為空資料；遷移須在全新測試世界／備份資料驗證，不修改使用者既有存檔。
- 既有程式的解碼失敗會留下空 Registry，不能宣稱已完整防護。新版本解碼失敗須阻止伺服器進入可玩狀態並記錄明確修復訊息，不能以空 Registry 繼續放行一般修改，也不自行覆寫／猜測紀錄。
- 純測試：供電與 enabled 分離、保護狀態、身分拒絕、碰撞占位、原生移除失敗、v1→新 schema 與錯誤資料拒絕。
- 原生 GameTest：無人／無 buff／門開仍能供電註冊與保護；held-high 後進人／補 buff／關門能 ARMED；held-high 不重複建立；低電位解鎖；錯 world 不解鎖。
- 跨程序重啟：powered／off／return-pending、同 UUID 重用、拆 Controller 後 record／索引消失。
- `clean build`、全套 JUnit／GameTests、production-only dedicated Done→stop，以及無 client class 載入錯誤。
- 人工 gate：單人外部拉桿→進艙→關門→喝藥，以及手持火把照明；M1.2 ARMED 不冒充 M2 空間延伸。
