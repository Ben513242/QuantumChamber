# M1–M6 驗證 harness

## M6 定向與 CI 入口

M6 Task 3 提供四個互斥 scope：default（其餘）、legacy（`m4_legacy_runtime`）、M5（`m5_universe*`）、M6（`m6_universe*`）。XML 依完整 `classname|name` 集合比對，拒絕缺漏、重複、跨 scope、錯 template、failure／error／skipped。同一 batch 可以有多個 testcase；M6 canary 的 `m6_universe_gate` 目前有兩個。

```powershell
pwsh -NoProfile -File scripts/verification/gates.ps1 -Mode M6Compile -Label task-compile
pwsh -NoProfile -File scripts/verification/m6-focused.ps1 -Suite GameTest -Batch m6_universe_gate -Label g0-green
pwsh -NoProfile -File scripts/verification/m6-focused.ps1 -Suite JUnit -TestClass dev.quantumchamber.persistence.PlayerCheckpointStoreTest -Label checkpoint-focused
pwsh -NoProfile -File scripts/verification/run-all.ps1
```

`M6Compile` 只編譯 main/client/test/testmod，不代替 GREEN。`M6JUnit` 選定 class 時核 exact suite、case 非空且不得 skipped；未指定 class 時執行全部 JUnit。`m6-focused` 每次先跑受控 scope／JAR／pace 反例，再跑 Move-Fresh 與 owned-root 回歸；受控空目錄殘留必被存在性斷言拒絕。正式 Move-Fresh 行為不變，所有 root 保留。`-Suite Probe -Chain <chain>` 在 Task 7 正式 runner 出現前以 `M6_PROBE_UNAVAILABLE` 拒絕。

M6 GameTest 用獨立 fresh `run/gametest-m6/world`，原世界可恢復 move／逐檔 hash exact restore。server 必帶唯一 `m6Only`、`minTickMillis=10`，不得註冊 M4 boundary 或 M5 suite-end observer；完整當次日誌的 pace 結束列恰一行，`waited>0`、`tps<=100.0`。full 同時核四 scope 與同 HEAD 的 M6 summary，並保留既有 release／sources、main-only 三層與 M3 固定 owner oracle。

CI 使用該 checkout wrapper／Gradle 8.8／Java 21，經 `m6-ci-gametest.ps1 -Platform Windows|Ubuntu` 執行 JUnit、legacy、M6，再核對四 run 的 exact 集合、pace 與內外 JAR 隔離。兩平台 M6 step 初始 15 分鐘、oracle 5 分鐘，原 job 上限 90 分鐘。Windows 原生 checkpoint／owned-process native chains 在 Ubuntu 不支援，`-CheckUnsupportedNative` 只在實際 Ubuntu 保存 `UNSUPPORTED` receipt；Windows 誤用或平台偽裝會被拒絕。

`ci-rule-check.ps1` 可加 `-M6GameTestXml`、`-M6RuntimeLog`、`-M6RuntimeRoot`、`-M6Artifacts`，複製到獨立 fixture 後執行 workflow 的 M6 oracle 原文。這是本機規則驗證，GitHub CI 成功另以遠端 run／exact SHA 證明。M6 native job／chains 的正式啟用屬 Task 12，此 task 未提前宣稱 native M6 通過。

以下 M1–M5 數字是歷史基準；M6 以當次 scope／summary 原件為準。

M1–M4 automated gates 的 tracked 版本。原本只放在 gitignored 的 SDD workspace `.superpowers/sdd/2026-09-21-m4-candidate-doors/`，刪除 worktree 或 `.superpowers/` 後就無法重跑；這裡的腳本只改路徑、參數與名稱，安全行為（fresh world move／逐檔 hash exact restore、owned roots、拒絕覆寫、main-only 三層 oracle、JAR testmod 檢查）與原始檔相同；PID 過濾等少數邏輯差異與拿掉的核對，逐項列在「來源對照」。

M5 的 gate 擴充也放在這裡。M5 F3c 新增 M5 GameTest run（M5 plan 決策 6）：會配置或物化 Universe、或會留下 M5 record 的 GameTest（batch 前綴 `m5_universe`），在獨立的 fresh 世界 `run/gametest-m5` 執行，不放在 default run。

F6-3e 的 CI 固定明列 default run 在 M5 期間新增的 33 個案例，以及 M5 run 全部 60 個案例；default 的總數仍是 179。比對使用 XML 的結構 `classname` 與完整 `name`（含 Java class 小寫前綴），不能只比方法名。既有 `_windows` 宣告掃描與平台略過規則照常適用；新增或搬動測試時，必須同步維護明列清單。

正常 M5 gate 以通過 SHA／順序檢查的完整當次日誌驗證：不得有 `M5_UNIVERSE_HOLD`；節流結束列恰一行，`waited>0`、`tps<=100.0`（不用 `waitedMs`）；`M5_UNIVERSE_SUITE_END` 保留 catalog 筆數、digest、converged 與 unfinished 的核對，另要求 `initialized=true`、allocation／projection／discovery／catalog 的 `Unconfirmed` 全部為 false。testmod 只在 `SERVER_STOPPING` 保留同 server 的既有權威參考，`SERVER_STOPPED` 讀當時旗標並在 finally 釋放，不建立、寫出或收斂權威。

## 執行

全部 gates（M5 F3c 時約 15 分鐘；F6-1 加上 M5 collapse probe 之後的實測耗時記在 M5 implementation note 的 F6-1 段；以下指令在 repo 根目錄執行，腳本本身依檔案位置找 repo root）：

```powershell
pwsh -NoProfile -File scripts/verification/run-all.ps1
```

成功時最後一行是 `END ALL exit=0 HEAD=<sha>`，倒數第二步印出 `SUMMARY ...`。任何步驟失敗都會印 `END <step> FAIL <原因>` 並停止。

重導 `run-all.ps1` 的輸出時，Gradle daemon 可能繼承外層管線，外層要等 daemon 結束才返回。以本次 `console.log` 的精確 `END ALL exit=0 HEAD=<sha>` 判完成；不能因外層仍等待而重跑已成功的 runtime，也不要為此終止 daemon。取證 pipeline 不使用 `Select-Object -First` 提前截斷執行中的腳本，否則 `finally` 可能無法完成。依本次 phase／run 的 receipt、nonce 與保存 root 定位日誌，不能讀前一 phase 的 `latest.log`。

`run-all.ps1` 不會因工作樹有未提交的變更而拒絕執行，只會在 `console.log` 的 `STATUS` 行列出 tracked 變更。一次 run 要能採計，需同時滿足三個條件：

1. `STATUS` 行沒有 `src/`、build 檔或 `.github/` 的變更。
2. 存在一個 commit C，本目錄每個 `.ps1`／`.gradle` 的 `HARNESS` 雜湊，都等於 C 中同一檔（`git show C:<path>`）的 SHA-256。
3. C 與 run 的 `HEAD` 之間，沒有 `src/`、build 檔或 `.github/` 的差異。

`HARNESS` 是工作樹 bytes 的雜湊。CRLF checkout 時，它不會等於 blob 內容的雜湊，這時改成兩步核對：先確認目前檔案的 SHA-256 仍等於 `HARNESS`，再確認 `git hash-object <path>` 等於 `git rev-parse C:<path>`。

個別執行：

```powershell
$v = 'scripts/verification'
& "$v/gates.ps1" -Mode Full -Label full            # 印出 GATE_ROOT=<gate root>
& "$v/gates.ps1" -Mode Legacy -Label legacy
& "$v/gates.ps1" -Mode M5GameTest -Label m5-gametest
& "$v/gates.ps1" -Mode Main -Label main-only
& "$v/main-oracle.ps1" -Gate <Main 的 GATE_ROOT>
& "$v/gates.ps1" -Mode M3 -Label m3                # -Only universe 或 -Only transfer 只跑一條
& "$v/m4-recovery-probe.ps1"                       # -Only chain,low 只跑指定 chain／scenario
& "$v/m5-collapse-probe.ps1"                       # -Only w2,w3 只跑指定 chain
& "$v/ci-rule-check.ps1" -Label win-green -Workflow .github/workflows/build.yml `
    -Step '確認 Windows 原生案例確實執行' -GameTestXml <Full gate>/result-build/gametest-results.xml `
    -M5GameTestXml <M5GameTest gate>/result-build/gametest-m5-results.xml `
    -JUnitDir <Full gate>/result-build/test-results/test -SourceRoot src/testmod/java
```

`ci-rule-check.ps1` 不因規則 FAIL 而 throw，判定看 `<root>/result.json` 的 `verdict`。要證明規則會擋下缺漏或宣告漂移，加 `-Mutation drop|skip|fail -MutationTarget <XML testcase name>`（`-MutationXml m5` 改對 M5 XML）或 `-SourceMutation interpose-annotation -SourceTarget <方法名稱>`，預期 `verdict=FAIL`。`-SourceMutation rename-windows` 把方法與它的 testcase 一起改名為 `<名稱>_windows`，用來驗證 `_windows` 規則的納入與排除（M5 的 `_windows` 案例：Windows step 要求出現在 M5 XML 並實際通過，Ubuntu step 不要求）。`-Mode GameTest`／`Windows`、`-Only` 與 mutation 模式在 2026-10-01 沒有單獨實跑；M5 F3c 實跑過的 mutation 記在 M5 implementation note 的 F3c 段。

## M2 cohort 的 CI-W1 故障驗證

在 repo 根目錄執行；`-Label` 只用英數與連字號。此入口固定使用既有的完整 default GameTest suite，不修改 `gates.ps1`；`-Only` 只屬於 M3，不能篩選 GameTest 案例。證據預設在被 gitignore 的 `.superpowers/verification/m2-cohort-failure/`；正式執行每次建立全新 fixture 與 gate root，原失敗 root 不重跑也不改寫。若另給 `-EvidenceRoot`，必須是本 worktree 內被忽略的路徑。

```powershell
pwsh -NoProfile -File scripts/verification/m2-cohort-failure-fixture.ps1 -Scenario partial-exception -Label ciw1-partial
pwsh -NoProfile -File scripts/verification/m2-cohort-failure-fixture.ps1 -Scenario slow-new60 -Label ciw1-slow -PrepareOnly
pwsh -NoProfile -File scripts/verification/m2-cohort-failure-fixture.ps1 -Scenario partial-exception -SourceGuardSelfTest
pwsh -NoProfile -File scripts/verification/m2-cohort-failure-fixture.ps1 -Scenario slow-old10 -OracleOnly `
    -GateRoot '<先前的 gate root>' -FixtureRoot '<先前的 fixture root>' `
    -OracleOutput '<同 worktree 忽略目錄內的新檔名>.json'
```

正式執行前確認沒有其他 runtime owner。入口核 Java source 與 HEAD 的 Git blob 一致，先備份原 bytes／SHA-256；adapter 只注入 testmod 的具名 south cohort，未命中的等待仍用原 predicate。正式 `gates.ps1 -Mode GameTest` 管理 fresh world 與逐檔 hash 還原；入口以同一個限制其他寫入的檔案 handle 比對與套用 source bytes，`finally` 僅在現值仍為本輪 mutation 時寫回原 bytes。若現值已是原 bytes，不再寫入；若檔案被外部改動、消失、成為 reparse path 或不可安全讀寫，保留現狀與見證，判 FAIL 並保留原 gate 錯。`-SourceGuardSelfTest` 僅用被忽略根的 disposable 檔案測試實際 guard 函式，不啟 Minecraft 或改正式 Java。fixture 的 `setup.json` 與 `verification-sources/` 保存本次三個腳本及本 README 的 bytes／SHA，後續文件更新不會使舊 root 的來源 pin 失效。含空白的路徑作為參數傳入即可；腳本以字面路徑操作，不用手動跳脫空白。

| `-Scenario` | 預期獨立判讀 |
| --- | --- |
| `partial-exception` | 真 partial/chunk 未就緒時受控丟出原錯；原 GameTest FAIL 前正式返還、關閉 owned 連線，下一 batch 的舊 SID 仍乾淨 |
| `timeout-false` | 測試 predicate 強制 false，證明具名等待有限失敗與收尾；不代表 production target 一直未就緒 |
| `slow-old10`／`slow-new60` | 同一具名 stage3 真 pending 時讓 server callback 一次暫停約 25 秒，恢復時仍逐字跑原 predicate；舊 10 秒應有限 FAIL 並清理，新 60 秒應待真 ready 後 PASS。這是受控排程停頓，不是原 Windows CI 時序的精確重現 |
| `request-fault` | 正式返還請求受控拋錯，獨立 witness 確認後仍安全關閉；原錯與 suppressed 請求錯保留 |
| `witness-fault` | 純 witness 持續故障至單一絕對上限；保留原錯、suppressed 與尚未關閉的連線證據，獨立判讀只確認有界失敗，不冒稱清理完成 |
| `late-crosswall` | 純查詢跨過原 wall deadline，後續不再請求或排程；正式返還 witness 成立後晚關閉，保留原 FAIL 與超時 suppressed，不誤記為期限內完成 |

`partial-exception` 等故障案例的**原** GameTest 應是 FAIL：入口只有在原 `execution.json` exit 1、唯一受控案例失敗、`gate.json` 明確記 `GameTest gate exit=1`、捕捉的 gateError 同樣精確，且獨立 oracle `PASS` 時才正常結束。`slow-new60` 則要求原 exit 0、XML 全綠、`gate.json` PASS 且沒有 gateError；scope／boundary 等正式 gate 後段錯誤不能被 cohort oracle 掩蓋。`-OracleOnly` 的 oracle FAIL 會使入口以非零結束，但不修改原 `execution.json`、XML 或 gate verdict。以 `ORIGINAL_GATE_EXIT`、`ORACLE_VERDICT` 分開判讀；細節在 fixture `oracle.json`、`restore.json`、`gate-control.json`、`gate-root.json`，gate 原件在其 `GATE_ROOT`。`-OracleOnly` 僅讀既有原 root 並寫新的報告，不啟動 Minecraft 或改 Java source。這份 fixture 驗證的是**已入場後七段 cohort 移動**的失敗收尾，不涵蓋最前段 `activeReady` 普通等待、其他 M2 caller 或正常 `trustedTeardown` 路徑。

## 新增 M5 GameTest

M5 的 GameTest 分在兩個 run：`M5CollapseGameTests`（default run，只用 SOURCE 或不配置宇宙的 fixture，結束時不留 M5 record）與 M5 run 的四個 class（`M5UniverseGameTests`、`M5UniverseProjectionGameTests`、`M5UniverseDoorGameTests`、`M5UniversePassageGameTests`，見下方第 1–8 點；F6-3c-2 由 `M5UniverseGameTests` 依主題拆出）。兩者共用 `src/testmod/java/dev/quantumchamber/gametest/` 下的 `M5GameTestSupport`（helper 與 fixture）與 `M5TestHooks`（mixin 讀取的靜態 hook）；M5 期間放在 `M4CandidateDoorGameTests` 的 test 也用同一份。`M5CollapseGameTests` 與 M5 run 的 class 不互相借用 helper：需要共用時，先搬進 `M5GameTestSupport`（或 `M5TestHooks`）。M5 run 的四個 class 之間共用的 helper 放 package-private 的 `M5UniverseSupport`，只有一個 class 用到的留在那個 class；catalog baseline、`begin`、`complete`／`awaitConvergedThenComplete` 與收斂的 hold 都在 `M5UniverseHold`（F6-3c-2）。

- **hook 釋放**：每個 test 建一個 `M2CorridorGameTests.TestHooks`，探針、log capture（`captureLogs(hooks)` 建立 capture 並登記關閉）、fixture 的收尾都登記在它上面（後進先出）。排程用 `at(context, tick, hooks, …)` 與 `whenTicks(context, tick, 上限, 條件, ready, 診斷, hooks)`（以 server tick 計的有界等待）：斷言失敗、逾時或例外時先 `releaseAfter`，成功路徑最後 `release()`。test 的程式不得讓例外從 `END_SERVER_TICK` 拋出（GameTest server 會崩潰）；探針只能在 journal flush 的開頭丟出受控的例外。
- **flush 探針與計數探針**：`installFlushProbe(context, probe, hooks)` 把探針裝在 `M5TestHooks.FLUSH_PROBE`（`SessionJournalWindowFaultMixin` 在每次 journal flush 的開頭呼叫）。探針與下一點的 journal 寫出稽核各是一個位置，同一時間只有一個持有者，安裝依序：先在 hooks 登記移除（hooks 已釋放時在這裡就丟出，什麼都不裝）；再在這個 test 的原版 `GameTestState` 登記 TestListener（test 結束時若仍裝著就移除，並記一行 `M5_TEST_HOOK_RESIDUE` WARN，涵蓋 tickLimit 逾時而 hooks 沒有釋放的情況）；最後才安裝。位置已被占用（同一個 batch 的另一個 test 正在使用，或沒有被移除的殘留）時丟 `IllegalStateException`、不覆蓋，訊息列出持有者的 test 與它是否已結束。「記 tick、前 N 次失敗」用 `new FlushFault(server, 訊息, N, 條件)`：條件成立的 flush 記下 server tick（`ticks()`），前 N 次在 flush 開頭受控失敗（`failures()`；之後照常寫出的是 `retries()`；`disarm()` 之後不再失敗）。條件只看 journal 的狀態（current 與 flushed），不分是誰呼叫 flush：只要帶著同一份未確認的變更，任何呼叫端的 flush（受測的寫入、recovery 的 RETRY_FLUSH、其他 session 的寫入）都會被計數，在前 N 次之內也會受控失敗，同一次要寫出的其他變更也跟著失敗。

- **塌縮流程的 log（規則）**：塌縮流程（`CollapseService` 與 F4a 起新增的 collapse 類別，例如 F5-0 的 `OriginDoors`）的每一則 log 都必須帶 SLF4J marker `CollapseService.LOG_MARKER` 或它的子 marker `TICK_LOG_MARKER`（不屬於任何 session 的，例如整個 tick 無法執行、原艙門的攔截在找出所屬 session 之前失敗）；能歸屬到 session 的 WARN／ERROR 在訊息中帶 `session=<UUID>`。JUnit `CollapseLogMarkerGuardTest` 掃描 `src/main/java/dev/quantumchamber/collapse/` 下所有 `.java` 守門：每個 `LOGGER.trace/debug/info/warn/error(` 的第一個參數必須是這兩個 marker（跨行的呼叫也算；註解與字串裡的字樣不算）；logger 只能是 `LOGGER = LoggerFactory.getLogger("quantumchamber")`（`LogCapture` 依 logger 名稱擷取），其他名稱的 Logger、`LOGGER` 當成值使用、`LogManager`、`System.out/err`、`printStackTrace` 都算違規；只有 `CollapseService` 可以宣告這兩個 marker。collapse package 以外的類別（例如 `universe` 的 `UniverseLifecycleService`）不在掃描範圍，守門範圍也不擴大：它們的 API 只回傳結果，不記塌縮流程的 WARN；塌縮流程的 WARN 一律在 collapse package 帶 marker 記錄。
- **log 斷言**：「這個 session 沒有塌縮流程的 WARN／ERROR」用 `collapseFlowNeverWarned(capture, sid)`：依 marker 篩選，不比對訊息字串；沒有 sid 的 tick 層級 WARN 以「capture 期間沒有帶 `TICK_LOG_MARKER` 的 WARN／ERROR」涵蓋。判定前它先以 marker 記一行 INFO 探針，capture 讀不到 marker 時丟例外。不分 marker 的「這個 sid 沒有任何 WARN／ERROR」用 `noWarnOrError(capture, sid)`。其他依 marker 的篩選用 `LogCapture.marked(level, marker, 片段…)`。log 斷言一律依 sid 篩選，不斷言絕對筆數或 tick。

- **前提**：
  - 用探針或稽核的 test 必須獨占一個 batch：同一個 batch 的 test 同時執行，第二個安裝會丟出。gate 只對 `m5_universe` 強制一個 test 一個 batch，default run 靠這條規則與安裝時的 fail-fast。
  - 有界等待的總長度（`whenTicks` 的上限、`afterAutosaveClear` 的等待與窗口、`awaitConvergedThenComplete` 的 maxTicks，加上呼叫時的 tick）要小於 `@GameTest(tickLimit = …)`。超過時原版判 test 逾時失敗，之後不再執行它的任何 callback：hooks 不會釋放，探針與稽核只由 TestListener 移除，其他收尾（fixture、log capture、玩家連線）都不會執行。
  - 等 PREPARE 完成（「準備完成」或 PASSAGE_READY）的有界等待：預載是 wall-clock 的 chunk 載入。原版 `TestServer` 不依 20 TPS 節流（`runTasksTillTickEnd()` 只做 `runTasks()`），tick 愈快，同一段預載用掉的 tick 愈多：F6-3b 之前，Ubuntu CI（600～1240 t/s）三次 run 有 16／1／7 個這類「有界等待逾時」，本機（約 1100 t/s）的 PREPARE 中位數約 200 tick、最多約 450 tick，也有偶發逾時。
    - **M5 run 的 tick 節流（F6-3b）**：testmod 的 `TestServerTickPaceMixin` 在 `TestServer.tick` 的開頭記下時間，`runTasksTillTickEnd` 在原版的 `runTasks()` 之後以 `runTasks(() -> 已到期限)` 等到「tick 開始＋最短時間」。等待期間照常執行 main-thread 的工作（不是單純 sleep），tick 本身已超過最短時間時不再等。它只在 system property `quantumchamber.gametest.minTickMillis`（1～1000 的整數毫秒，不合法時開服即失敗）存在時生效，`build.gradle` 只在 `gameTestM5` run 設為 10：每個 tick 至少 10 ms，也就是最多 100 t/s。真實伺服器是 20 TPS（每 tick 50 ms），節流之後更接近實際情況，不是在遮掩 production 的問題。default 與 legacy run 不加：default run 的 175 個在 Ubuntu 三次都通過，它的等待不靠 PREPARE 的預載。不要用 `/tick rate` 代替：TestServer 不等 tick 的結束時間，它沒有節流效果，還會改變 autosave 的間隔（`afterAutosaveClear`）。節流確實生效看得到（F6-3b fix round 1）：第一次實際等待時記一則 INFO（`GameTest tick 節流：每個 tick 至少 10 ms（…）；第 N 個 tick 第一次實際等待`），停服時（`TestServer.exit` 的開頭）再記一則 INFO `GameTest tick 節流 結束：ticks=… waited=… waitedMs=… elapsedMs=… tps=… minTickMs=10`（節流適用的 tick 數、其中實際等待的次數與時間，以及由 wall-clock 估出的 t/s）；F6-3e 起 gate 以完整當次日誌要求結束列恰一行、waited>0 與 tps<=100.0。`waitedMs` 是那幾段等待的 wall-clock，**包含**等待期間照常執行的 main-thread 工作，不是閒置時間（F6-3c-1），不要拿它當「節流多花的時間」或斷言的依據。
    - 節流之後本機的 PREPARE 只用 1～21 tick（設計成要等的除外），400 tick 的窗口至少等 4 秒。F6-3b 量過每個 `whenTicks` 窗口在節流之後的餘裕（M5 note 的 F6-3b 一節）：等 wall-clock 的窗口都在 2 倍以上，預載另外慢 800 ms 時也有 5 倍以上，所以沒有放寬任何窗口；不足 2 倍的只有等 production 以 tick 計的計時（退避 200／400 tick、通道 1200 tick）或依構造不會逾時的窗口，用掉的 tick 不隨機器快慢改變。
    - 上限仍以 production 的 §9.1 門檻 600 tick 為天花板（`CollapseService.WAIT_WARN_TICKS`，從進入 PREPARE 起算；超過時 production 自己記 PREPARE 等待的 WARN，而 M5 test 多半斷言沒有 WARN），`tickLimit` 跟著留足。F6-2c Step 0 起 `passage_ends_with_a_plain_open_door_when_the_source_loses_power` 與 EXISTING 再造訪、退化的三個 test 中 D1 的準備用 600 tick（F6-3c-1 起四處共用 `PREPARE_WAIT_TICKS`（F6-3c-2 起在 `M5UniverseSupport`），理由寫在它的 Javadoc）；其他 test 等 PREPARE 的窗口多半是 400 tick。
  - fixture 的呼叫時點：`whenRegistered`、`whenEntered` 以呼叫當下的 tick 為基準，可以在 test 方法本體（t0=0）或任何 callback 裡呼叫。在 callback 裡呼叫時，它們會在原版迭代 runAtTick 表的途中插入項目（供電與第一次檢查各一項）；同一個 callback 要再排很多項時，留意第 5 點說明的 rehash 風險。

會配置或物化 Universe、或會留下 M5 record 的 GameTest（M5 plan 決策 6）：

1. 依主題放進 `src/testmod/java/dev/quantumchamber/gametest/` 下 M5 run 的四個 class 之一：`M5UniverseGameTests`（catalog 的 harness 自我測試、RESOLVE 與目的地的確定）、`M5UniverseProjectionGameTests`（投影與 PREPARE）、`M5UniverseDoorGameTests`（原艙門與找不到所屬 session 的量子膜）、`M5UniversePassageGameTests`（量子通道）。gate 要求 batch 前綴 `m5_universe` 的 test 都在這四個 class（`gates.ps1` 的 `$M5RunClasses`；F6-3c-2 起，原本只有 `M5UniverseGameTests`）。新增第五個 class 時，同步改 `$M5RunClasses` 與 testmod `fabric.mod.json` 的 `fabric-gametest` entrypoint；`.github/workflows/build.yml` 的兩個檢查 step 以 batch 前綴掃描全部 testmod 原始碼，不列 class，不用改。
2. 一個 test 一個 batch：`@GameTest(templateName = "quantumchamber:m1_empty", batchId = "m5_universe_<名稱>")`，`<名稱>` 不和其他 test 共用。batch 依序執行，逐 test 的 catalog 增量才只屬於該 test；共用 batch 時 gate 會失敗。
3. 名稱以 `_windows` 結尾的 test（需要 Windows 原生 checkpoint）：平台略過（`if(!Platform.isWindows()) { context.complete(); return; }`）放在 `begin` 之前，略過時不留下 baseline。Windows 上每個 test 都必須走到最後一步並通過，gate 逐 test 要求一行 PASS 的增量。
4. 第一個動作（平台略過之後）是 `begin(context, "<方法名稱>")`，名稱必須等於方法名稱。它在不是 M5 run 時、在碰 catalog 之前就讓 test 失敗，也檢查開始時已收斂。
   - **失敗不連坐（F6-3b B1，盤點 U6）**：一個 test 在權威寫出失敗之後、收斂之前就失敗時（例如 Windows 原子移動的 AccessDenied），production 只在下一次使用之前收斂，沒有人會替它收斂；原版又在同一個 tick 開始下一個 batch，所以 F6-3b 之前後面每個 test 的 `begin` 都立刻失敗（最多連坐 59 個）。F6-3b 起，M5 run 的每個 test 由原版初始化之前（testmod 的 `M5ConvergenceHoldMixin`，掛在 `GameTestState.tick` 的開頭，只在 `m5Only` 時生效）先問 `M5UniverseHold.holdBeforeBegin`：四個 M5 權威都已收斂時立刻放行（純查詢，行為與原版相同）；有未確認的寫入時，每個 tick 對四個權威各呼叫一次 `convergeIfNeeded`（退避照 production），收斂之後才初始化這個 test，最多等 600 tick（3×`CollapseBackoff.INITIAL_TICKS`；test 的 tickLimit 從初始化之後才起算）。逾時仍未收斂時放行，由 `begin` 照舊失敗。失敗的那個 test 照常 FAIL，只是後面的 test 不再連坐。
     - **前一個 test 通過時不吞掉（F6-3b fix round 1）**：通過的 test 只在 `finish` 完成的那一刻保證已收斂（PASS 的條件含收斂），之後仍可能留下未確認的寫入（同一個 tick 其他的收尾、batch 結束時取消強制載入、之後 tick 的 production）。hold 以「最後一個呼叫 `begin` 的 test」在原版的結果（`GameTestState.isPassed()`，不是 `finish` 寫的 PASS 行）判斷前一個 test：失敗或沒有前一個 test 時照上面的做法；**通過**時記一則 ERROR，照常嘗試收斂（收斂的話再下一個 test 不受影響），並讓下一個 `begin`（通常就是 hold 等的那個 test）以「前一個 test（`<名稱>`）通過之後仍留下未確認的權威：[…]」失敗。F6-3c-1 起這個原因在 hold 放行時才寫成，帶 hold 的結果與等了多久（`…；hold 的結果：converged，heldTicks=<N>）`；逾時是 `timeout（仍未收斂：[…]）`，判定丟出例外是 `error（<例外>）`）。所以所有 test 都通過、test 之間也沒有留下未確認寫入的 run，不會有任何 `M5_UNIVERSE_HOLD` 行。
     - log（都以 `M5_UNIVERSE_HOLD` 開頭）：開始是 WARN `start`（帶前一個 test 與它的結果，例如 `previous=<名稱>(FAIL)`；沒有前一個 test 時是 `previous=none`），前一個 test 通過時改為 ERROR `after-pass`；結束是 INFO `converged`，或 WARN `timeout`（仍未收斂，接下來的 `begin` 會失敗）、WARN `error`（判定丟出例外，放行，由 `begin` 判定）。
5. 最後一個動作二選一：
   - `awaitConvergedThenComplete(context, <預期的 catalog 增量>, <maxTicks>[, <ready 條件>])`：每個 tick 主動呼叫 `CollapseAuthorities.convergeIfNeeded`（catalog 是 checked flush），收斂（而且 ready 條件成立）之後才完成，逾時就失敗。可以在 `waitAndRun`／`runAtTick` 的 callback 裡呼叫：輪詢由專用的 `TimedTaskRunner` 執行，不會在原版迭代 `runAtTick` 的表時插入項目。完成時點之後才到期的 `runAtTick`／`waitAndRun` 檢查不會執行：還沒到期的檢查，必須放進 ready 條件，或排在呼叫 helper 之前、而且在呼叫時已經到期。ready 條件用回傳 false 表示「還沒好」；ready、權威收斂與判定丟出的例外都轉成 test 失敗，不會讓 GameTest server 崩潰。
   - `complete(context, <預期的 catalog 增量>)`：當下就判定。未通過時保留 baseline、不寫增量行，所以可以放在 `context.addInstantFinalTask(() -> complete(context, n))` 裡逐 tick 重試；但只能在最後一步之後註冊（例如在最後一個 `waitAndRun` 的 callback 裡呼叫）。在 test 開頭就註冊的話，runner 從那個 tick 起每個 tick 都嘗試，catalog 增量一達標就 complete，之後排定的檢查不會執行，等於誤判 PASS。判定丟出非 GameTestException 的例外（例如 catalog 不健康）時，complete 把它轉成 GameTestException、之後一直丟同一個，並以原版的 `TimedTaskRunner.fail` 讓 test 確定失敗：在 runner 裡時下一個 tick 失敗，直接呼叫或在 callback 裡時同一個 tick 失敗，不必等 tickLimit，也不會讓 server 崩潰。runner 工作裡自己寫的其他程式碼，也不要丟出非 GameTestException 的例外（原版的 runner 只攔 GameTestException）。
6. 注入失敗的 test，要等 catalog 與四個 M5 權威都收斂之後才完成（衛生規則），否則之後的 NEW 配置會一直等待。權威寫出失敗之後的退避從 200 tick 起跳（`CollapseBackoff.INITIAL_TICKS`，之後加倍），所以這類 test 的 `maxTicks` 要超過 200，`@GameTest(tickLimit = …)` 也要跟著加大（預設 100）。
7. tick 上限：`maxTicks` 要小於 test 的 `tickLimit` 減去呼叫時的 tick。超過 `tickLimit` 的那一個 tick，原版一律判 test 失敗：即使同一個 tick 剛收斂、已寫了 PASS 的增量行也一樣；還沒收斂時以「等待…」的訊息失敗，不會留下 `status=FAIL` 的增量行。
8. 用 `gates.ps1 -Mode M5GameTest`（或 `run-all.ps1`）跑。直接執行 `gradle runGameTestM5` 時，`run/gametest-m5/world` 必須是 fresh 的：gate 從 0 筆開始串接增量，固定 UUID 的 fixture 在舊世界中也會撞到既有紀錄。

「哪些 test 屬於哪個 run」有三份實作：`gates.ps1` 的 `Batch-Scope`／`Declared-GameTests`，以及 `.github/workflows/build.yml` 的兩個檢查 step（「確認 Windows 原生案例確實執行」「確認非 Windows 跨平台案例確實執行」）。CI step 只能是 workflow 內的 `run: |` 原文（`ci-rule-check.ps1` 逐字抽出執行），沒辦法共用腳本，所以三處必須同步：都掃描 `src/testmod/java` 下全部 `*.java`；掃描前先去掉註解行（去掉前導空白後以 `//`、`/*`、`*` 開頭的行，含 Javadoc 內的 `{@code @GameTest}`）；嚴格掃描是 `@GameTest(...)` 緊接 `public void <名稱>(TestContext`；前綴規則是 `m4_legacy_runtime` 屬 legacy run、前綴 `m5_universe` 屬 M5 run、其餘屬 default run（與 testmod 的 `M4LegacyGameTestFilterMixin` 相同）。改其中一處時，三處與 filter 一起改，並以 `ci-rule-check.ps1` 與 M5 gate 重跑。

- 每條 chain 建一個新的 owned root `run/m5-collapse-<runId>-<chain>`，每個 phase 一個 JVM：Gradle `runM5Collapse`，也就是 `build.gradle` 的 `m5Collapse` run。這個 run 刻意不帶 `-Dquantumchamber.test.collapseSuspended=all`（M4 recovery 用的全域暫停），probe 也斷言 JVM 參數裡沒有它。
- phase evidence 由 testmod 固定在 `.superpowers/sdd/2026-10-01-m5-collapse-passage/collapse-<nonce>/<phase>/`，不受 `-EvidenceRoot` 影響；彙整在 `-EvidenceRoot` 的 `collapse-run-<runId>.json`。phase evidence 已存在時拒絕執行（禁止重跑）。
- chain 表的每個 phase 標記預期的結束：
  - `stop`：Gradle exit 0、JVM exit code 0、`final.json` 的 status 為 `PASS`（另有 `stoppingSeen`、`stoppedSeen`、`stopRequested`），沒有 `halt.json`。
  - `halt`：JVM 在 crash 窗口寫出 `halt.json`（CREATE_NEW＋force）之後以 `Runtime.halt(77)` 結束，不經正常停止、不存檔，等同 crash。腳本要求：Gradle 非 0、JVM exit code 77（找到 JVM 時先取得 process handle，結束之後以它讀 exit code）、Gradle 輸出有 `finished with non-zero exit value 77`、`halt.json` 的 status 為 `HALT` 而且窗口相符、沒有 `final.json`。窗口沒有到達或斷言失敗時，probe 正常停止並寫 FAIL 的 `final.json`，腳本判 FAIL。
  - halt 必須乾淨（F6-2a）：crash 點的第一次 hit（`hit` 1）、crash 點沒有記下失敗（`crashPointFailure` 為 `none`）、`failures` 是空的，而且停服還沒有開始（F6-2c Step 0）。任何一項不成立時 probe 不當成 crash：status `HALT_REFUSED`（`refused` 列出原因；停服之後是 `stoppingSeen`）、exit 78。腳本、`run-all.ps1` 與 restart 讀回 halt receipt 時（`crashReceiptClean`）也都核對前三項。另外，`SERVER_STOPPING` 一開始（早於 production 的 listener）probe 就移除自己安裝的全部 hook，不經請求停服的停服（例如 crash report 的路徑）也不會再觸發 crash 點。
- 兩種結束都核對：receipt 的 PID、StartTime、startupNonce 與實際的 JVM 相符、標示 testmod runtime；JVM 已結束；`world/session.lock` 可以獨占開啟。同一條 chain 的每個 phase，PID@StartTime 與 startupNonce 都不同。
- 三份表的一致性（F6-2a）：receipt 的 `ending` 必須等於 chain 表的預期結束；receipt 的 `phaseTable`（probe 的整張 phase 表）必須與 `$chains` 的全部 phase 依序相同，任何一邊多出或少了 phase 都判 FAIL。第三份表是 `run-all.ps1` 的 `$expectedCollapse`；run-all 會逐份 receipt 再核對 `phaseTable`，必須等於已核名稱／順序／ending／window 的本次 phases。
- 失敗訊息：主要 exit／receipt 檢查的錯誤訊息附上 `final.json`／`halt.json` 的 status 與 failures（halt 另有 hit、crashPointFailure、refused）；halt 的 phase 先看 `final.json`，所以「窗口沒有到達、斷言失敗而正常停止」直接看得到原因。
- 共用程序管理（F6-3d-2）：`m4-recovery-probe.ps1`、`m5-collapse-probe.ps1` dot-source 小型 `probe-common.ps1`；每個 caller 明確傳入 Context/State，仍各自保留 phase 表、receipt oracle、world/session.lock 檢查。M4 改為以已持有的 handle 判斷退出，不會把仍可列舉的已退出程序物件誤判為 live JVM。
- 逾時：兩個 wrapper 都使用 `-IdleSeconds`（預設 90）及 `-PhaseMinutes`（預設 8）；M4 的總上限維持原本 8 分鐘，新增 idle 預設與 M5 一致。找到 JVM 後，latest.log／stdout／stderr 任一長度變動都重設 idle；total 從 launcher 啟動時計算。逾時仍判 FAIL、保留 root，不可同 root 重跑。
- 終止前同時核對已保存的 PID/handle/StartTime、nonce commandline，以及最新 CIM `CreationDate`（容許小於 1 ms 的時間精度差異）；jstack 取證後再核一次才以原 handle 終止 JVM。JVM 尚未找到時先重新查 nonce，確認當下沒有該 JVM才核對並結束本次 launcher handle；不掃殺子程序、不終止 Gradle daemon。查詢失敗或身分不符就保留程序與診斷，不推定沒有啟動；下一次執行前仍須核對原 root owner。
- 編碼：`-GradleCodePage` 預設目前文化的 OEM code page（此 zh-TW 環境為 950）；launcher 明確設定自己的 console/output encoding，stdout/stderr 依該編碼讀取。server 的 latest.log 固定以 UTF-8 讀取，BOM 優先；不修改機器地區設定。`timeout.json` 的 `encodings` 與正常 `launcher.json` 的 `logEncodings` 記錄來源編碼。
- 診斷：`timeout.json` 保留既有原因、exit、jstack 與最後 20 行，新增 `identityCheck`、`identityBeforeKill`、`discoveryError`、`launcherPid`、`launcherIdentity`、`launcherKilled`、`encodings`。正常 `launcher.json` 新增 `auxiliaryLogs`（classload/latest 各有 source/present/copied）與 `logEncodings`；輔助 log 缺少只記錄，不因此額外 FAIL，必要 receipt/identity/lock/oracle 仍照常守門。Java receipt 與彙整原欄位不變。
- halt 的 `window` 大小寫必須精確相符，錯誤帶 receipt note。entrypoint 失敗時，錯誤附上 latest.log 的 `Could not execute entrypoint` 段（前 80 行及該段其餘 `Caused by:`），保留原本 exit/receipt 判定；log 只當資料，不執行其中內容。

## 當次完整日誌與失敗取證

`gates.ps1` 在每次 Invoke-Gradle 開始前保存 `logs-before.json`；結束時將原日誌保存在該 execution 的 `runtime-logs/`，另產生 `runtime-log.json` 與 `runtime-full.log`。manifest 帶啟停 UTC、launcher／觀察到的 JVM 身分、原 root、每個 piece 的原始／展開 SHA、順序與選入／排除理由。先排除未變檔與前次內容（包括開服時把前次 latest 輪替成新 archive），再按 archive 日期與數字序號、最後 latest 串接當次內容；不依時間戳逐行過濾，stack trace 的無時間行也會保留，原 latest 不改寫。

```powershell
. ./scripts/verification/gate-evidence.ps1
$complete = Read-GateRuntimeLog -Evidence '<本次 gate>/execution'
```

reader 會重核 pieces、順序與完整輸出 SHA；run-all 的 per-test consumer 與 summary 也實際使用此入口。比較 WARN／ERROR 時以這份完整內容為來源，不能只讀殘缺 latest。Main gate 會還原原 `run/server`，所以持久入口是 gate 的 execution 保存副本，完成後不能以已還原的 `run/server/logs` 冒充當次。

F6-3e 起當次 manifest 為 schema 2：成功的 Minecraft invocation 至少要有一份非空當次 piece。沒有檔案、只有舊內容、當次內容為空，分別記為 `missing-log-files`、`no-current-pieces`、`empty-current-pieces`，並拒絕取證成功。純 Windows JUnit／明確的編譯 invocation，以及已失敗的 invocation，明列不適用；不適用模式不能包含任何 `run` task。reader 保留 schema 1 的歷史讀回能力。取證診斷錯誤寫入 `capture-errors.json`，原 exception 或非零 exit 優先，不由診斷錯誤取代。

Invoke-Gradle 遇到 timeout／exception／非零 exit 時仍先 flush stdout／stderr，保存 `execution.json`、當次日誌與 `failure-artifacts.json`／`failure-xml/`。XML 依開始前 SHA／mtime 及能否完整解析分類為 `current-complete`、`stale`、`incomplete`；當次完整只代表取證完整，不代表失敗 run 通過。診斷或複製錯誤另記 `capture-errors.json`，不取代原 exception。停止、owner、鎖與世界還原契約不變。

M5 collapse probe 維持本機 run-all，不加入 CI（既有 X2(a) 裁示）。它依賴 Windows `Win32_Process` 的 commandline／CreationDate 與 Java 21 `jstack`，69 個 phase 各啟一個 JVM，含 31 個預期 HALT；不能把單一測試的時間當成整條 chain 預算。`w12` 最後檢查到 tick620，在正常 20 TPS 約 31 秒，另加開服、worldgen、存檔與停服時間；每 phase 的 `PhaseMinutes=8`、`IdleSeconds=90` 分別限制總 wall-clock 與無進展時間，任一失敗就停止 chain。整輪正常實測時間以 note 的採計 run-all 為準；F7 再整理正式限制。歷史 `h5/sample-jstack.ps1`／`red.ps1` 保留為歷史取證，不追蹤化或修改。
